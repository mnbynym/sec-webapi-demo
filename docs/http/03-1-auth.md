# 03-1-auth.http の解説

テキスト 3-1「認証」に対応する。認証そのもの（パスワードの照合とトークンの発行）は Supabase Auth に任せ、API は受け取った JWT の検証だけを行う構成を確認する。

```text
クライアント ──(1) メール + パスワード──▶ Supabase Auth
            ◀─(2) access_token（JWT） ───
クライアント ──(3) Authorization: Bearer <JWT>──▶ API（FastAPI）
                                                  └─ 署名・期限・aud を検証（Supabase に問い合わせない）
```

## 1. ログイン（alice）

**レスポンス（主な項目）**

```json
{
  "access_token": "eyJhbGciOi…",
  "token_type": "bearer",
  "expires_in": 3600,
  "refresh_token": "…",
  "user": { "id": "…", "email": "alice@example.com", … }
}
```

**ポイント**

- アクセストークンの有効期限は 1 時間（`expires_in: 3600`）と短く、期限が切れたらリフレッシュトークンで新しいアクセストークンを取得する。
- `access_token` を jwt.io などでデコードして、中身（ヘッダーとペイロード）を確認する。JWT は署名されているだけで暗号化はされていないので、誰でも中身を読める。秘密情報を入れてはいけない理由になる。

**ペイロードの主なクレーム**

| クレーム | 内容 |
|---|---|
| `sub` | ユーザー ID。API はこれで「誰か」を判断する |
| `aud` | 想定する受信者（`authenticated`）。API はこの値を検証する |
| `iss` | 発行者（Supabase Auth の URL） |
| `exp` / `iat` | 有効期限 / 発行日時（UNIX 時刻） |
| `email`、`role`、`session_id` など | Supabase が付与する情報 |

`role: "authenticated"` は Supabase の DB 権限用の値で、このアプリの管理者権限とは別物。このアプリでは、管理者かどうかを JWT ではなく DB（`profiles.role`）で判断している（3-2）。

## 2. 公開鍵（JWKS）

```http
GET {{sb}}/auth/v1/.well-known/jwks.json
```

**レスポンス**

```json
{ "keys": [ { "kty": "EC", "crv": "P-256", "kid": "…", "alg": "ES256", "x": "…", "y": "…" } ] }
```

**ポイント**

- 非対称鍵（ES256 / RS256）で署名されている場合、API は JWKS から公開鍵を取得して署名を検証する。秘密鍵は Supabase だけが持ち、API は公開鍵しか持たないので、API から鍵が漏れてもトークンは偽造できない。
- JWT のヘッダーの `kid` で、どの鍵で署名されたかを判別する。鍵をローテーションしても、JWKS に新旧の鍵を並べておけば無停止で切り替えられる。
- API は公開鍵をキャッシュし、未知の `kid` が来たときだけ取り直している（`app/auth.py` の `PyJWKClient`）。

Supabase の設定によっては、HS256（共有鍵）で署名されていて、`keys` が空になることがある。その場合、API は `.env` の `SUPABASE_JWT_SECRET` で検証している。共有鍵は、検証する側も署名できてしまう（漏れると偽造される）ため、非対称鍵の方が安全。

## 3. API 側での検証結果

```http
GET /v1/auth/whoami
```

**レスポンス**

```json
{
  "sub": "…",
  "email": "alice@example.com",
  "alg": "ES256",
  "kid": "…",
  "aud": "authenticated",
  "issuer": "http://127.0.0.1:54321/auth/v1",
  "expires_at": "2026-10-16T02:30:00Z"
}
```

**ポイント**

- API は、署名、有効期限（`exp`）、受信者（`aud`）を検証し、`sub` をユーザー ID として扱う。
- 検証は API の中だけで完結し、リクエストのたびに Supabase へ問い合わせない（ステートレス）。そのぶん速いが、ログアウトや権限変更をしても、発行済みのトークンは期限まで有効なままになる。アクセストークンの有効期限を短くする理由。

実装は `app/auth.py` の `verify_token` にある。

## 4. 署名を改ざんしたトークン

トークンの末尾に `x` を付けて送る。

- ステータス：`401`
- ボディ：`detail: トークンを検証できません`

ペイロードを書き換えたトークンも、署名が一致しないので同じく拒否される。

## 5. alg=none のトークン

ヘッダーが `{"alg": "none"}` で、署名のないトークンを送る。

- ステータス：`401`
- ボディ：`detail: 許可されていない署名アルゴリズムです: none`

**ポイント**

- JWT の仕様には「署名なし」を表す `alg: none` がある。ヘッダーの `alg` をそのまま信じて検証するライブラリだと、署名なしのトークンが通ってしまう（過去に実際にあった脆弱性）。
- 受け付けるアルゴリズムは、サーバー側で許可リストとして固定する（`ES256`、`RS256`、`HS256`）。
- 同じ理由で、公開鍵を HS256 の共有鍵として使わせる攻撃（アルゴリズムの混同）も、許可リストと鍵の種類の対応を固定することで防ぐ。

## 6. リフレッシュトークンでの更新

```http
POST {{sb}}/auth/v1/token?grant_type=refresh_token
{"refresh_token": "{{alice.response.body.$.refresh_token}}"}
```

**レスポンス**

- 新しい `access_token` と、新しい `refresh_token` が返る。

**ポイント**

- リフレッシュトークンは 1 回使うと新しいものに置き換わる（Refresh Token Rotation）。
- 古いリフレッシュトークンが再び使われた場合、盗まれた可能性があるとみなして、そのセッションのトークンをまとめて無効にする（再利用の検知）。Supabase では、通信の再送などに備えて短い猶予時間（既定 10 秒）が設けられている。
- リフレッシュトークンは長期間有効なので、アクセストークン以上に厳重に扱う。ブラウザなら `HttpOnly` の Cookie に保存し、JavaScript から読めないようにするのが基本。

## 補足

- このデモではデータを変更しないので、`make reset` は不要。
- 6 を実行した後も、1 で取得したアクセストークンは期限まで有効なまま（ステートレスな検証の性質）。
