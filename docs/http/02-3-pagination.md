# 02-3-pagination.http の解説

テキスト 2-3「ページネーション・フィルタ・ソート」に対応する。注文 100 万件を持つ alice で、オフセット方式とカーソル方式の違いを確認する。後半は MongoDB の商品検索で、フィルタと返却フィールドの絞り込みを確認する。

応答時間は、REST Client のレスポンス画面のステータスバー（下部）に表示される。差がはっきり出るのは、シード件数を既定値（注文 100 万件）にしている場合。

## 1. ログイン（alice）

## 2. カーソル方式：1 ページ目

```http
GET /v1/orders?limit=5
```

**レスポンス**

```json
{
  "data": [ …5 件… ],
  "pagination": { "next_cursor": "eyJjcmVhdGVkX2F0Ijoi…", "has_more": true, "limit": 5 }
}
```

**ポイント**

- 並び順は `created_at` の降順で、同じ時刻の注文があっても順序が揺れないように `id` をタイブレーカーにしている（`order by created_at desc, id desc`）。ソート順が一意に決まらないと、ページの境目で同じ注文が 2 回出たり抜けたりする。
- `next_cursor` は、最後の注文の `created_at` と `id` を JSON にして Base64URL でエンコードしたもの。中身をクライアントに意識させない（不透明な文字列として扱わせる）ことで、内部の実装を後から変えられる。
- 総件数は返さない。総件数を数えるには全件の走査が必要になるため（下の COUNT の項を参照）。

## 3. カーソル方式：2 ページ目

```http
GET /v1/orders?limit=5&cursor={{page1.response.body.$.pagination.next_cursor}}
```

- 1 ページ目の続きの 5 件が返る。
- SQL は `where (created_at, id) < (カーソルの値) order by … limit 6` になる。インデックス上の目的の位置から必要な件数だけを読むので、何ページ目でもコストが変わらない。
- `limit` より 1 件多く取得し、6 件目があれば `has_more: true` にしている。総件数を数えずに「次があるか」を判定する定番の方法。

## 4. オフセット方式：浅いページ

```http
GET /v1/orders?limit=5&page=1
```

**レスポンス**

```json
"pagination": { "page": 1, "per_page": 5, "total_count": 1000000 }
```

- `total_count` が返るので、「全 200,000 ページ中 1 ページ目」のような画面を作りやすい。
- 浅いページは速い。オフセット方式の問題は、深いページで表面化する。

## 5. オフセット方式：深いページ（10 万ページ目）

```http
GET /v1/orders?limit=5&page=100000
```

**ポイント**

- `limit 5 offset 499995` になり、DB は読み飛ばす 49 万 9,995 行もすべて処理してから 5 件を返す。カーソル方式の 2 ページ目と応答時間を比べる。
- 実行計画で見ると、差はさらに明確になる。ターミナルで `make explain-pg` を実行する（50 万件目以降の 20 件を取得）。

| 方式 | 実行時間（例） | 走査ページ（例） |
|---|---|---|
| オフセット | 約 370 ms | 約 25,000 |
| カーソル | 約 0.1 ms | 4 |
| COUNT(*)（総件数） | 約 90 ms | 約 25,000 |

- オフセットが深いと、プランナーはインデックスを使わずに全件を読んでソートする方を選ぶことがある。さらにソートが `work_mem` に収まらず、一時ファイルへの書き込み（`temp written`）が発生する。
- ページの途中に新しい注文が追加されると、オフセット方式ではページの境目がずれて、同じ注文が次のページにも表示される。カーソル方式ではずれない。

## 6. フィルタ：ステータス + 作成日時の範囲 + 昇順

```http
GET /v1/orders?status=shipped&created_at_gte=2026-09-01T00:00:00Z&sort=created_at&limit=5
```

**ポイント**

- フィルタは、フィールド名をそのままクエリパラメータにし、範囲は `_gte` / `_lte` の接尾辞で表している。
- ソートは `sort=created_at`（昇順）/ `sort=-created_at`（降順）の形式。`-` 接頭辞で降順を表す。
- 受け付けるソート項目は列挙型で制限している（任意の列名を受け付けると、インデックスのない列でソートされたり、SQL インジェクションの入口になったりする）。
- インデックスは `(user_id, status, created_at desc, id desc)` の順に定義している。等値条件（user_id、status）→ ソート（created_at、id）→ 範囲条件（created_at）の順にすると、絞り込みとソートの両方にインデックスが効く（ESR ルール）。

## 7. 400：改ざんされたカーソル

```http
GET /v1/orders?cursor=invalid!!
```

- ステータス：`400`
- ボディ：`type: /problems/invalid-cursor`

デコードできないカーソルは 400 で拒否する。カーソルの中身はクライアントが組み立てるものではない、という約束を API 側で守らせる。

## 8. 商品検索（MongoDB）：等値 + 範囲 + ソート

```http
GET /v1/products?category=books&price_gte=1000&price_lte=5000&limit=5
```

**レスポンス**

- ヘッダー：`Cache-Control: public, max-age=30`、`RateLimit-Policy`、`RateLimit`（3-3 のレートリミット）
- ボディ：books カテゴリで価格が 1,000〜5,000 円の商品が、作成日時の降順で 5 件返る。

**ポイント**

- MongoDB でも、カーソル方式のページネーションと、`_id` をタイブレーカーにしたソートを使っている。
- インデックスは `category`（等値）→ `created_at`, `_id`（ソート）→ `price`（範囲）の順に定義している（ESR ルール）。効果は `make explain-mongo` で確認できる。

| インデックスの順序 | キー走査（例） | ドキュメント走査（例） | メモリソート |
|---|---|---|---|
| ESR（等値 → ソート → 範囲） | 103 | 20 | なし |
| ERS（等値 → 範囲 → ソート） | 2,543 | 2,543 | あり |

- 範囲条件を先に置くと、範囲に該当する全件を読んでからメモリ上でソートすることになる。直感に反して「範囲はソートの後」にするのがポイント。
- `q`（商品名の部分一致）も使える。ユーザー入力は正規表現としてそのまま使わず、エスケープしている（3-4）。

## 9. Sparse Fieldsets：返却フィールドの絞り込み

```http
GET /v1/products?category=books&fields=sku,name,price&limit=5
```

- `sku`、`name`、`price` の 3 つだけが返る。
- 一覧画面では説明文などの大きなフィールドが不要なことが多い。転送量と DB からの読み込み量を減らせる。GraphQL（1-1）では、これが言語仕様として備わっている。

## 10. 400：未知のフィールドの指定

```http
GET /v1/products?fields=sku,password
```

- ステータス：`400`
- ボディ：`detail: 未知のフィールド: password`

指定できるフィールドは許可リストで制限している。存在しないフィールドを黙って無視すると、クライアントの誤りに気付けない。また、内部用のフィールドを指定されて漏れる事故も防げる。

## 補足

- 商品一覧はレートリミット（容量 10、毎秒 2 補充）の対象。続けて何度も実行すると 429 になるので、数秒待つ。
- このデモではデータを変更しないので、`make reset` は不要。
