# 03-3-ratelimit.http の解説

テキスト 3-3「レートリミット」に対応する。商品一覧 API（未認証でも呼べる）に、トークンバケット方式のレートリミットをかけている。REST Client ではヘッダーの変化と 429 を確認し、連続したリクエストの様子は Node と k6 で確認する。

## トークンバケットの設定

| 項目 | 値 | 意味 |
|---|---|---|
| 容量 | 10 | 一度に連続で送れるリクエスト数（バースト） |
| 補充速度 | 毎秒 2 | 長期的に許容する平均のリクエスト数 |
| キー | 接続元 IP | 商品一覧は未認証で呼べるため、IP 単位で数える |

リクエストのたびにトークンを 1 つ消費し、空なら 429 を返す。トークンは時間とともに補充される。短時間のバーストは許しつつ、平均の速度は抑えられるのがこの方式の特徴。

実装は `app/ratelimit.py` にある。状態（残りトークン数と最終更新時刻）を Redis に置き、判定と更新を Lua スクリプトで 1 回の操作として実行している。API を複数台に増やしても、全台で同じカウンタを共有でき、同時アクセスでも数え漏れが起きない。

## 1. RateLimit ヘッダーの確認

```http
GET /v1/products?limit=1&fields=sku
```

**レスポンス**

```http
RateLimit-Policy: "products-search";q=10;w=5
RateLimit: "products-search";r=9;t=1
```

**ポイント**

- IETF のドラフト（RateLimit header fields for HTTP）の現行の形式。`RateLimit-Policy` で制限の内容、`RateLimit` で現在の状態を伝える。
- `q=10;w=5` は「5 秒の窓で 10 リクエスト」、`r=9` は残り 9 回、`t=1` はリセットまでの秒数を表す。
- 以前のドラフトの `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset` の 3 ヘッダーは、この 2 ヘッダーに統合された。GitHub などの `X-RateLimit-*` は、標準化前の独自形式。
- クライアントは `r` を見て、上限に達する前に送信の間隔を空けられる。

## 2. 連打して 429 を確認する

同じリクエストの **Send Request** を素早く 10 回以上押す。

**レスポンス**

- ステータス：`429 Too Many Requests`
- ヘッダー：`Retry-After: 1`、`RateLimit: "products-search";r=0;t=5`
- ボディ：`type: /problems/rate-limited`、`detail: 1 秒後に再試行してください`

**ポイント**

- 429 には `Retry-After` を付け、何秒待てばよいかを伝える。クライアントはこの値に従って再試行する（4-4 のリトライでも、この値を尊重している）。
- エラーの形式は、ほかのエラーと同じ Problem Details（2-4）。
- 429 は「クライアントが送りすぎている」ことを示し、503（サーバーが過負荷・停止中）とは区別する。

REST Client の手作業では速さが足りず、429 まで行かないこともある。その場合は下の Node クライアントで確認する。

## ターミナルでのデモ

### npm run ratelimit

```bash
npm run ratelimit
```

```text
① バースト：容量 10 を使い切ると 429
10:15:01.120 # 1 200  RateLimit: "products-search";r=9;t=1
…
10:15:01.310 #10 200  RateLimit: "products-search";r=0;t=5
10:15:01.330 #11 429  RateLimit: "products-search";r=0;t=5  Retry-After: 1
…
② 3 秒待つとトークンが補充される（毎秒 2）
10:15:04.350 #16 200  RateLimit: "products-search";r=5;t=3
```

最初の 10 回は通り、11 回目から 429 になる。3 秒待つと約 6 トークンが補充され、再び通るようになる。

### make k6-ratelimit

```bash
make k6-ratelimit
```

毎秒 10 リクエストを 20 秒間送り続ける。補充は毎秒 2 なので、最初のバースト分を除くと、通るのは約 2 割になる。結果のカスタムメトリクス `allowed_200` と `rate_limited_429` の比率で確認する。

## 設計上の考慮点

- **キーの選び方**：認証が必要な API ならユーザー ID（トークンの `sub`）、未認証なら IP をキーにする。IP だけだと、同じ会社や携帯キャリアの NAT の背後にいる利用者がまとめて制限される。API キーやテナント単位で、別の上限を設けることもある。
- **プロキシの背後での IP**：ロードバランサーや CDN の背後では、API から見える接続元はプロキシの IP になる。`X-Forwarded-For` から実際の IP を取り出す必要があるが、このヘッダーはクライアントが偽装できる。信頼するプロキシが付けた部分だけを使う設定にする。
- **エンドポイントごとの上限**：ログインやパスワードリセットのように、総当たり攻撃の対象になる API は、より厳しい上限にする。重い処理の API はトークンの消費量（コスト）を大きくする方法もある（このデモの `rate_limited(cost=...)`）。
- **レートリミットだけでは足りない**：分散した大量の IP からの攻撃（DDoS）は、API サーバーに届く前に WAF や CDN で防ぐ。

## 補足

- このデモではデータを変更しない。トークンは時間で回復するので、`make reset` は不要（すぐに回復させたい場合は `make reset` で Redis を初期化できる）。
- 商品一覧を使うほかのデモファイル（02-3 など）も、同じ上限を共有している。
