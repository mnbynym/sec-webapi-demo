# 04-4-resilience.http の解説

テキスト 4-4「タイムアウト・リトライ・サーキットブレーカー」に対応する。在庫 API は、下流の在庫サービスを呼び出して結果を返す。下流との間に Toxiproxy を挟み、遅延や停止を外から注入して、API がどう振る舞うかを確認する。

```text
REST Client ──▶ API /v1/inventory/{sku} ──▶ Toxiproxy :18000 ──▶ 在庫サービス /_downstream/inventory/{sku}
                 （タイムアウト 1.5 秒）       ↑ make chaos-* で遅延・停止を注入
```

在庫サービスはデモを単純にするため API と同じプロセスに同居させているが、別サービスとして扱う。

REST Client で確認するのは API 側（サーバー）の振る舞い。クライアント側のリトライとサーキットブレーカーは、後半の Node のデモで確認する。

**ターミナルを 2 つ用意し、片方で `make chaos-*` を実行しながら進める。**

## API 側のタイムアウトの設定

| 項目 | 値 | 意味 |
|---|---|---|
| 接続タイムアウト | 0.3 秒 | TCP 接続の確立までの上限。到達できない相手を早く見切る |
| 読み取りタイムアウト | 1.5 秒 | 応答を待つ上限 |
| 全体の予算 | 2 秒 | クライアントがデッドラインを指定しない場合の既定値 |

呼び出し元（クライアント）より呼び出し先（API → 在庫サービス）のタイムアウトを短くするのが原則。逆にすると、クライアントが諦めた後も API が下流を待ち続け、無駄な処理とリソースの占有が連鎖する。

## 1. 正常時

```http
GET /v1/inventory/SKU-000001
```

**レスポンス**

- ステータス：`200`
- ヘッダー：`Server-Timing: downstream;dur=55`
- ボディ：`{"sku": "SKU-000001", "available": 55, "warehouse": "osaka", "stale": false}`

**ポイント**

- `Server-Timing` は、サーバー内部の処理時間をクライアントに伝える標準ヘッダー。ブラウザの開発者ツールでも表示される。
- 成功した結果は、障害時の縮退応答（後述の 5）に使うため、Redis に保存している。

## 2. 遅延の注入：504 Gateway Timeout

```bash
make chaos-latency   # 下流に 3 秒の遅延を注入
```

同じリクエストを送る。

**レスポンス**

- 約 1.5 秒後に、ステータス：`504`
- ボディ：`type: /problems/upstream-timeout`、`detail: 1.50 秒以内に応答がありませんでした`

**ポイント**

- 下流は 3 秒かかるが、API は 1.5 秒で見切ってエラーを返している。タイムアウトがなければ、クライアントは 3 秒（実際の障害ではもっと長く）待たされる。
- 下流の遅延に引きずられて API のワーカーや接続がすべて待ち状態になると、在庫と関係のない API まで応答できなくなる。これが障害の連鎖（カスケード障害）。タイムアウトは、その連鎖を断ち切る最初の防御になる。

## 3. デッドラインの伝播

```http
GET /v1/inventory/SKU-000001
X-Request-Deadline: {{$timestamp 1 s}}000
```

`{{$timestamp 1 s}}` は「現在から 1 秒後」の UNIX 時刻（秒）で、末尾に `000` を付けてミリ秒にしている。

**レスポンス（遅延を注入したまま）**

- 約 1 秒後に `504`（2 のときより早い）

**ポイント**

- クライアントが「この時刻までに結果が欲しい」という締め切りをヘッダーで伝えている。API は残り時間を計算し、下流を待つ時間を 1.5 秒から残り時間（約 1 秒）に縮める。
- API は下流にも、残り時間を `X-Request-Deadline` で引き継いでいる。下流は、締め切りまでに終わらない処理は始めない。サービスが何段にも連なる場合でも、全体の締め切りが守られる。
- gRPC では、この仕組みが標準機能（`grpc-timeout`）として組み込まれている（1-1 の gRPC デモ）。

`make chaos-reset` で遅延を解除してから送れば、締め切り内に終わるので `200` が返る。

## 4. 停止の注入：503 Service Unavailable

```bash
make chaos-down   # 下流への接続を拒否する
```

同じリクエストを送る。

**レスポンス**

- ステータス：`503`（すぐに返る）
- ヘッダー：`Retry-After: 1`
- ボディ：`type: /problems/upstream-unavailable`、`detail: 在庫サービスに接続できません`

**ポイント**

- 下流がタイムアウトした（504）のか、接続できなかった（503）のかを区別して返している。クライアントが再試行の判断に使える。
- `Retry-After` で、再試行までの待ち時間を伝える。

## 5. 機能縮退（フォールバック）

```http
GET /v1/inventory/SKU-000001?fallback=true
```

下流を止めたまま送る。

**レスポンス**

- ステータス：`200`
- ヘッダー：`Cache-Status: webapi-demo; fwd=stale; detail=upstream-failure`
- ボディ：`{"sku": "SKU-000001", "available": 55, "warehouse": "osaka", "stale": true}`

**ポイント**

- 下流が使えないとき、エラーにする代わりに、最後に取得できた値を「古い値である」と明示して返している。商品ページで在庫数が少し古くても、ページ全体がエラーになるよりはよい、という判断。
- `stale: true` と `Cache-Status` ヘッダー（RFC 9211）で、古い値であることをクライアントに伝える。
- 縮退してよいかは業務次第。在庫の表示なら古くてもよいが、注文確定時の在庫引き当てに古い値を使ってはいけない。どの機能をどこまで縮退させるかは、事前に決めておく。
- 1 の正常時のリクエストを実行していないと、保存された値がないので 503 になる。

デモが終わったら復旧させる。

```bash
make chaos-reset
```

## ターミナルでのデモ：クライアント側の回復性

```bash
npm run resilience
```

在庫 API を 0.5 秒間隔で 40 回呼び出しながら、別のターミナルで `make chaos-latency` → `make chaos-down` → `make chaos-reset` の順に障害を切り替える。

```text
10:20:01.100 # 5 [closed   ] 200 52ms
    retry #1 after 143ms (504)
    retry #2 after 361ms (504)
10:20:06.800 #12 [closed   ] failed (504)
  ⚡ circuit closed → open
10:20:07.300 #13 [open     ] short-circuit（下流へ送らず即時失敗）
  ⚡ circuit open → half-open
  ⚡ circuit half-open → closed
10:20:14.900 #25 [closed   ] 200 48ms
```

**ポイント**

- **タイムアウト**：クライアントは 2.5 秒で諦める（API の 1.5 秒より長くしている）。`AbortSignal.timeout` を使う。
- **指数バックオフ + Full Jitter**：再試行の間隔を `0〜min(上限, 基準 × 2^n)` の乱数にしている。全クライアントが同じタイミングで再試行すると、復旧しかけたサーバーに一斉にアクセスが集中する（リトライストーム）。乱数で分散させる。
- **リトライの対象**：429、502、503、504、ネットワークエラーだけを再試行し、400 や 404 は再試行しない。何度送っても結果が変わらないため。POST を再試行するなら、4-2 の Idempotency-Key が前提になる。
- **リトライバジェット**：再試行の回数を、全リクエストの 20% 以内に抑えている。障害時に再試行で負荷が数倍に膨らむのを防ぐ。
- **サーキットブレーカー**：直近 10 回の失敗率が 50% を超えると「open」になり、5 秒間は下流に送らずに即座に失敗させる。障害中のサービスに追い打ちをかけず、クライアントも待たされない。5 秒後に「half-open」で 1 回だけ試し、成功すれば「closed」に戻る。

## 片付け

```bash
make chaos-reset
```

このデモではデータを変更しないが、障害の注入を解除し忘れると、ほかのデモ（`make doctor` など）が失敗する。`make reset` でも解除される。
