# 04-2-idempotency.http の解説

テキスト 4-2「冪等性」に対応する。注文作成（POST）に `Idempotency-Key` を付け、通信の再送やボタンの二度押しがあっても注文が二重に作られないことを見せる。後半は、注文作成のイベントを別サービスに確実に届ける Transactional Outbox と、重複したイベントを無視する冪等コンシューマを見せる。

**このファイルは、`make reset` をしてから実行する。** 冪等キーは 24 時間記録されるので、リセットせずに 2 回目を実行すると、1 つ目のリクエストから「再生」の結果になる。

## Idempotency-Key の動き

| 状況 | API の応答 |
|---|---|
| 初めてのキー | 処理を実行し、結果を保存してから返す |
| 同じキー・同じ内容で、処理が完了済み | 処理をせず、保存した結果をそのまま返す（`Idempotent-Replayed: true`） |
| 同じキーで、処理がまだ実行中 | `409 Conflict`（少し待って再試行させる） |
| 同じキー・違う内容 | `422`（キーの使い回しの誤りとして拒否） |
| 処理が失敗した | キーを解放し、同じキーでの再試行を許す |

キーはクライアントが生成する（UUID など）。仕様は IETF のドラフト（The Idempotency-Key HTTP Header Field）に沿っている。実装は `app/idempotency.py` にある。

## 1. ログイン（alice）

## 2. 1 回目：201 Created

```http
POST /v1/orders
Idempotency-Key: demo-4-2-0001
{"items": [{"sku": "SKU-000020", "quantity": 1}]}
```

**レスポンス**

- ステータス：`201`（処理時間の再現のため、約 0.3 秒かかる）
- ヘッダー：`Location: /v1/orders/{id}`
- ボディ：作成された注文。`id` を控えておく。

## 3. 2 回目（同じキー・同じ内容）：保存済みの結果を再生

**レスポンス**

- ステータス：`201`
- ヘッダー：`Idempotent-Replayed: true`、`Location` は 1 回目と同じ
- ボディ：1 回目とまったく同じ（同じ `id`）

**説明のポイント**

- 2 回目は注文を作らず、1 回目に保存したレスポンスをそのまま返している。応答も速い（処理を実行しないので待ち時間がない）。
- クライアントから見ると、1 回目の応答が通信の途中で失われた場合でも、同じキーで再送すれば、二重注文の心配なく結果を受け取れる。4-4 の自動リトライを安全に行うための前提になる。
- GET、PUT、DELETE は HTTP の仕様上もともと冪等だが、POST は冪等ではない。そのため、POST にはこの仕組みが必要になる。決済 API（Stripe など）で広く使われている方式だ。

## 4. 同じキーで内容を改ざん：422

```http
Idempotency-Key: demo-4-2-0001
{"items": [{"sku": "SKU-000020", "quantity": 99}]}
```

**レスポンス**

- ステータス：`422`
- ボディ：`type: /problems/idempotency-key-reused`、`detail: 同じ Idempotency-Key で異なる内容が送信されました`

**説明のポイント**

- API は、キーと一緒にリクエストの内容（メソッド、パス、ボディ）のハッシュを保存している。同じキーで内容が違えば、クライアントのバグ（キーの使い回し）とみなして拒否する。
- 黙って前回の結果を返すと、クライアントは「数量 99 で注文できた」と誤解してしまう。

## 5. キーなし：送るたびに別の注文ができる

同じリクエストを、キーなしで 2 回以上送る。

- 送るたびに `201` が返り、毎回違う `id` の注文が作られる。
- 応答が返らなかったときに再送すると、注文が二重にできてしまう。これが冪等性を担保しない場合のリスクだ。

## ターミナルでのデモ

### 同時送信：npm run idempotency

REST Client では「処理中」の状態を作れないので、Node で同じキーのリクエストを同時に 5 本送る（二度押しや、タイムアウト直後の自動リトライを再現する）。

```bash
npm run idempotency
```

```text
① 同時に 5 リクエスト（1 件だけ処理され、残りは処理中の 409）
  request #1               201 019a…
  request #2               409 同じ Idempotency-Key のリクエストを処理中です
  request #3               409 同じ Idempotency-Key のリクエストを処理中です
  …
② 完了後に同じキーで再送（保存済みレスポンスを再生、同じ注文 ID）
  retry                    201 (replayed) 019a…
③ 同じキーで内容を変更（改ざんとみなして 422）
  tampered                 422 Idempotency-Key が別の内容で再利用されました

作成された注文: 1 件 019a…
```

**説明のポイント**

- 5 本のうち、キーの登録に最初に成功した 1 本だけが処理を実行する。登録は DB の主キー制約（`INSERT … ON CONFLICT DO NOTHING`）で行っているので、同時に届いても 2 本が同時に処理を始めることはない。
- 「処理中」の 409 には `Retry-After: 1` を付けている。クライアントは少し待って再送すれば、完了済みの結果を受け取れる。

### Transactional Outbox と冪等コンシューマ

別のターミナルで outbox のリレーを起動しておくと、注文作成のイベントが処理されるログが流れる。

```bash
make relay
```

```text
outbox consumed order.created 019a…
```

次に、配信済みのイベントを意図的に重複配信する。

```bash
make relay-redeliver
```

```text
outbox skip duplicate event 019a…
```

**説明のポイント**

- 注文の登録と「注文が作成された」イベントの記録を、同じ DB トランザクションで outbox テーブルに書き込んでいる。注文だけ登録されてイベントが失われる（あるいはその逆）ことが起きない。
- リレーは outbox を読んで配信し、成功したら配信済みの印を付ける。配信の直後に印を付ける前に落ちると、同じイベントがもう一度配信される（At-least-once）。重複はなくせないので、受け取る側で排除する。
- 受信側（MongoDB の集計）は、イベント ID を一意キーとして記録し、記録済みなら処理をスキップする（冪等コンシューマ）。`make relay-redeliver` で、重複配信がスキップされることを確認できる。
- API の Idempotency-Key（送信側の重複対策）と、冪等コンシューマ（受信側の重複対策）は、同じ考え方を両端に適用したものだ。

## 片付け

```bash
make reset
```

作成した注文、冪等キー、outbox、MongoDB の集計が削除される。
